# PINNED, deliberately, including transitive dependencies.
#
# This file is a lock, not a range. The versions below are the exact set that
# ran successfully in production on 2026-08-19 (run 32258951498), copied from
# that run's install log.
#
# WHY A LOCK AND NOT A RANGE
#
# The previous file said `requests>=2.31,<3` and friends, so every run resolved
# fresh against PyPI. That is fine for a project someone looks at weekly, and
# wrong for this one: the entire design goal is to run unattended for months. A
# minor release with changed behaviour would break collection with no change on
# our side, and -- because CI only ran on push -- the first place it would show
# up is a live collection day. Fares missed on an index day cannot be
# recollected, so "find out in production" is the one outcome worth paying to
# avoid.
#
# The obvious objection is that pinning means never learning that a newer
# version breaks us. That is handled rather than accepted: `airfares-ci` runs a
# weekly `latest-deps` job that installs UNPINNED and runs the suite. It is
# allowed to fail. So the pins keep production reproducible while the canary
# gives early warning, and neither job depends on the other.
#
# HOW TO UPDATE
#
# Let Dependabot open the PR (see .github/dependabot.yml) and let CI judge it.
# By hand: relax to the direct dependencies below, install, and paste back
# `pip freeze`. The three that are actually ours are:
#
#     requests                 HTTP for the fare provider and the ONS fetchers
#     google-cloud-bigquery    the append-only panel
#     openpyxl                 reads the ONS .xlsx release
#
# Everything else is transitive and pinned only so the set is reproducible.
